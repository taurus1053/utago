# 우타고(Utago) — 기획 정리

*최초 초안 리뷰 및 논의 내용을 정리한 문서입니다. (2026-09-22 기준)*

## 0. 종합 전략 요약 (최종 방향)

**"콘텐츠 가공은 AI로 자동화해서 속도를 내고, 문법 학습 + 진짜 양방향 다국어 구조로 차별화하며, 저작권 리스크는 개인 프로젝트 단계에 맞게 현실적으로 받아들이되 가사 원문만큼은 최대한 깨끗한 경로로 확보한다."**

- **음원**: YouTube 우선 (무료 접근성, 영상 노출 방식으로 정책 준수 — 우타코토 사례로 실증됨). Apple Music/Spotify는 해당 서비스 이용자가 **자기 계정을 연결해서** 쓸 수 있는 옵션으로 병행 제공 (2순위, 온보딩에서 선택 가능).
- **가사 원문 확보**: LRCLIB 등 출처 불명 크롤링 DB 의존은 피하고, 직접 타이핑하거나 유튜브 공식 자막(CC) 등 최대한 설명 가능한 경로로 확보.
- **콘텐츠 가공(후리가나/번역/단어추출/문법설명)**: **AI 자동화 파이프라인**으로 처리(우타코토 사례로 기술적 실현 가능성 확인). 사람은 결과물 검수만 담당. → "AI 보조 큐레이션" 방식.
- **DB 저장**: 가공된 콘텐츠(원문, 번역, 후리가나, 단어, 문법 설명)는 **중앙 DB에 저장하여 여러 사용자에게 재사용**하는 구조로 감 (곡마다 매번 재가공하지 않기 위함). 이는 저작권 노출도가 있는 선택이라는 걸 인지한 상태로, 개인 프로젝트·소규모 단계의 실질적 리스크는 낮다고 보고 진행 — 경쟁 앱들(우타코토 등)도 동일한 방식으로 이미 운영 중.
- **카탈로그 규모**: 완전 자동 대규모 검색도, 극도로 제한된 수작업 큐레이션도 아닌 "AI 보조 큐레이션" — 1단계 목표는 초기 50~100곡.
- **차별화 포인트**: ① 문법 학습 페이지, ② 진짜 양방향 다국어 구조(모국어별 발음 자동 전환) — 경쟁 3사 모두 없음, 계속 밀고 감.
- **힘 뺄 영역**: SRS·플래시카드·게이미피케이션(스트릭 등)은 이미 경쟁작들이 구현 — 최소 기능만 갖추고 차별화 포인트에 리소스 집중.
- **2단계 전환 시점**: 수익화·트래픽 확대 = 법적 리스크 확대 시점으로 인식하고, 그때 Musixmatch B2B·LyricFind 등 정식 라이선스 전환 + 변호사 상담 진행. *(Claude는 법률 전문가가 아님 — 실제 수익화 임박 시 전문가 상담 필수)*

---

## 1. 컨셉

좋아하는 노래의 가사를 통해 언어를 학습하는 앱. 일본어부터 시작해서 한국어, 영어까지 다국어 지원 예정.

## 2. 앱 이름

**우타고 (Utago)** — 歌(uta, 노래) + 語(go, 언어)의 합성어로 확정. 짧고 간결한 발음, 향후 다국어 확장 시에도 자연스럽게 어울리는 브랜드명.

## 3. 핵심 기능 (원본 기획 초안)

1. 노래 선택 → 음원+가사 로드, 재생 시 소절 단위로 가사가 나오며 해당 소절에 쓰인 단어의 뜻/예문이 아래 표시. 일본어는 후리가나 표시.
2. 가사 후리가나 on/off 토글
3. 가사 아래 발음 표시 — 사용자 모국어에 따라 자동 전환 (한국어 사용자: 한글 발음 / 일본어 사용자: 가타카나 / 영어권: 로마자)
4. 전체 가사 드롭다운 + 클릭 시 해당 구간으로 이동 (유튜브 뮤직 스타일)
5. 표시된 단어를 단어장에 추가하는 버튼
6. "문법 공부하기" 버튼 → 해당 곡의 핵심 문법 정리 페이지로 이동
7. 단어장은 폴더처럼 사용자가 직접 카테고리 생성 가능
8. 단어장 플래시카드 암기: 안다/모른다로 넘기며 진행, 1회독 후 셔플 여부 선택, 모든 단어가 "암"이 될 때까지 반복. 중도 종료 시 확인 절차.
9. 플래시카드 암기 시 (일본어 기준): 한자 단어 → "일어 예문 보기" → 일어 예문 표시 (버튼이 히라가나 버튼으로 전환되어 후리가나 노출) → "한국어 예문 보기" → 한국어 예문
10. 단어장 내 별표(즐겨찾기) 기능 — 즐겨찾기 단어장은 기본 제공, 별도 생성 불필요

## 4. 강점 / 차별점

- "좋아하는 노래"라는 정서적 진입점 → 범용 학습 앱 대비 지속 동기부여에 강함
- 모국어 기반 발음 자동 전환 설계가 처음부터 다국어 확장을 고려한 구조
- 플래시카드의 단계적 노출(한자→일어 예문→한국어 예문)로 문맥 기반 암기 가능
- 유튜브 뮤직 스타일 UX로 학습 진입 장벽이 낮음
- 즐겨찾기 단어장 기본 제공 등 디테일한 사용자 배려
- 단어-문법-발음-듣기가 하나의 콘텐츠(노래) 안에서 통합되는 학습 경험
- **(경쟁사 분석 후 재확인)** 문법 학습 페이지, 완전한 다국어·양방향 구조는 경쟁 앱들에 없는 실질적 차별화 지점 — 자세한 내용은 7번 항목 참고

## 5. 논의를 통해 정해진 방향

### 음원 소싱 — 최종
**YouTube를 1순위**로 확정. 무료 접근성이 가장 넓고, 우타코토 사례로 "영상 노출 + 학습 UI 결합"이 실제로 어색하지 않게 작동한다는 게 검증됨.

**[검증 결과]** YouTube 개발자 정책상 "오디오와 영상을 분리·격리하는 행위"는 명시적으로 금지되어 있고, 플레이어를 오버레이로 가리거나 숨기는 것도 금지됨 (최소 200×200px 노출 필요). 즉 **실제 유튜브 영상 화면이 사용자에게 보여야 함** — UI 설계 시 반영.
(참고: [YouTube API 개발자 정책](https://developers.google.com/youtube/terms/developer-policies), [필수 최소 기능 정책](https://developers.google.com/youtube/terms/required-minimum-functionality))

**Apple Music/Spotify는 2순위**: 해당 서비스를 이미 이용 중인 사용자가 **자기 계정을 연결해서** 광고 없이 쓸 수 있는 옵션으로 병행 제공 (온보딩에서 선택 가능하게, 우타노트 사례 참고). 상업적 이용 약관은 추후 확인 필요.

**[실사용 확인]** 우타코토: YouTube 영상이 재생 컨트롤·워터마크까지 그대로 노출되는 방식으로 실제 서비스 중. 우타노트: 온보딩에서 Apple Music/Spotify 선택, 단 음악 검색 연동이 실사용 중 불안정(에러 발생) — API 연동 난이도를 넉넉히 잡을 것.

### 가사 데이터 소싱 & 콘텐츠 제작 — 최종: "AI 보조 큐레이션"

처음 검토했던 LRCLIB(오픈 가사 동기화 DB)는 실사 검증 결과 **법적 회색지대** 프로젝트로 확인되어(Musixmatch 등에서 긁어온 데이터+익명 업로드, 운영자 스스로도 무단 사용 인지) 부적합 판단.

**콘텐츠 가공은 AI로 자동화한다는 게 핵심 변화**: 경쟁 앱 우타코토를 실사용해본 결과, "유튜브 링크 → 음원·자막 가져오기 → 가사·후리가나 추출 → 번역·발음 생성 → 단어 분석·JLPT 분류"가 **완전 자동 파이프라인**으로 구현되어 있고, 자동 처리 실패 시에만 사람이 "검수 중" 상태로 확인하는 구조임을 확인. 이는 저희가 처음 가정했던 "곡당 1~2시간 수작업"이 AI로 크게 단축될 수 있다는 실증 사례.

**→ 우타고의 1단계 콘텐츠 파이프라인**:
1. **원문 텍스트 확보**: 직접 타이핑 또는 유튜브 공식 자막(CC) 등 최대한 출처를 설명할 수 있는 경로로 확보 (LRCLIB류 출처 불명 크롤링 DB 의존 지양)
2. **AI 자동 가공**: 후리가나, 한/일/영 번역, 발음 표기, 단어 추출, 예문, 문법 설명까지 AI(LLM)로 자동 생성
3. **사람 검수**: 자동 생성 결과를 검수 후 게시 (우타코토의 "검수 중" 상태 개념 차용)
4. **DB 저장 및 재사용**: 가공된 콘텐츠는 중앙 DB에 저장해 모든 사용자에게 서비스

**[중요 — 저작권 리스크 재확인]** DB에 저장해서 여러 사용자에게 재사용하는 구조는 **"이미 있으니 안전하다"는 뜻이 아니라, 오히려 저작물을 다수에게 복제·배포하는 전형적 형태에 가까움**. 우타코토가 "이미 등록된 곡은 포인트가 적게 든다"고 한 것도 법적 안전성이 아니라 AI 처리 비용을 아끼기 위한 캐시 재사용일 뿐. 우타고도 이 리스크를 원래부터 받아들이기로 한 것(개인 프로젝트 단계의 실질적 리스크는 낮다고 판단)과 동일한 선상 — 다만 "DB에 있어서 괜찮다"는 인식은 정확하지 않다는 점을 유의.

**대안 모델 참고**: 우타노트는 사용자가 Musixmatch 웹뷰에서 직접 텍스트를 복사해 개인적으로 붙여넣고 수작업 싱크하는 "사용자 도구 제공자" 포지션이라 법적으로 상대적으로 안전한 모델. 우타고가 향후 사용자 참여형 기능을 추가할 때 참고 가치 있음.

**카탈로그 규모 목표**: 1단계 초기 50~100곡 (AI 가공으로 순수 수작업 대비 훨씬 빠른 처리 가능).

**전환을 매끄럽게 하기 위한 설계 원칙 (유지)**:
- DB/콘텐츠 구조를 소싱 방식과 분리 설계 — AI 가공이든 향후 라이선스 데이터 자동 임포트든 동일한 "노래-소절-가사-단어" 스키마 사용
- 곡마다 출처(provenance) 필드 기록 (원문 확보 경로, AI 가공 여부, 검수 여부 등)

**유의사항**: 본격 수익화 시점에는 저작권 신탁단체(한국음악저작권협회 등)나 퍼블리셔와 정식 라이선스 체결을 진지하게 검토해야 함. *(Claude는 법률 전문가가 아니므로, 실제 수익화를 앞둔 시점에는 변호사·저작권 전문가 상담을 권장)*

### 언어 범위
**일본어 · 한국어 · 영어** 3개 언어로 우선 개발. 검증 후 글로벌 확장 시 주요 언어 추가 고려.

### 단어 DB 구조
- 소절 아래 표시되는 뜻: **의역** (문맥에 맞는 자연스러운 번역)
- 단어 하나하나의 뜻/발음/예문: 노래와 무관한 **중앙 마스터 사전 테이블**에 한 번만 등록해 모든 노래에서 재사용 (콘텐츠 제작 병목 완화)
- 다의어 처리: 문맥별 의미를 노래마다 매핑하지 않고, **자주 쓰이는 의미 몇 가지를 사전식으로 나열**하는 방식 (파파고 사전 표시 참고). 소절 의역이 실제 문맥 의미를 전달하므로 단어 팝업은 일반적 의미 안내 역할로 충분.
- 사전 데이터는 기존 라이선스 사전(예: 엣센스 일한사전류) 또는 JMdict 등 오픈 사전 자원을 시드로 활용 검토
- **(경쟁사 참고 — 트레이드오프)** 우타코토는 단어 예문을 범용 사전 예문이 아니라 **같은 곡의 다른 소절에서** 가져와 붙임 (맥락 몰입감 ↑, 콘텐츠 제작 부담 ↑). AI 자동 가공 파이프라인을 쓰면 이 방식도 부담 없이 채택 가능 — "곡 내 맥락 예문 우선, 없으면 마스터 사전 예문" 하이브리드 고려

### SRS(간격 반복) 접목
기존 "학습 세션"(회독JLPT 스타일: 안다/모른다 반복, 전부 암기될 때까지 셔플 반복) 구조는 유지하되, 그 위에 **"복습 큐"**를 별도로 추가:
- 단어별로 `다음 복습일`, `현재 간격(일수)`, `연속 정답 횟수` 필드 관리
- "안다" → 간격 증가(1일→3일→7일→14일…), "모른다" → 간격 초기화
- 홈 화면에 "오늘 복습할 단어" 목록 제공 (SM-2 알고리즘 단순화 버전)
- 플래시카드 UI(예문 보기, 히라가나 토글, 별표 등)는 학습/복습 모드 공통 재사용
- **(경쟁사 참고)** 우타코토가 이미 SRS + 스와이프형 플래시카드 + 객관식 퀴즈를 구현 중이라, 이 자체는 더 이상 독자적 차별점이 아니며 완성도로 승부해야 함 (힘 뺄 영역)

### 게이미피케이션 & 레벨
- **사용자 레벨**(게임화 요소)과 **콘텐츠 난이도**(어학 등급)를 명확히 분리
- 사용자 레벨: JLPT/CEFR과 무관하게 앱 내 활동(학습 단어 수, 복습 횟수, 스트릭 등) 기반 경험치 레벨
- 콘텐츠 난이도: 내부 추천 알고리즘용으로만 관리, N1 등 시험 등급 라벨은 사용자에게 노출하지 않음 (학습 압박감 방지) — **[재검토 필요]** 우타코토는 단어 카드마다 N5~N1 라벨을 전면에 노출하고 있고 평점도 양호함. 온보딩에서 레벨 표시 on/off를 사용자가 선택하게 하는 절충안 검토
- 추가 기능: 타임어택 단어 매칭 미니게임, 빈칸 채우기/딕테이션 퀴즈, 섀도잉·발음 평가(STT), 학습 리포트(스트릭, 학습 단어 수 등 통계) — 힘 뺄 영역, 최소 기능만
- **[통계 화면 벤치마크]** 우타코토의 "통계" 탭 구성 참고: 연속 학습일·주간 스트릭·오늘 복습량 카드, 깃허브 잔디밭 스타일 학습 달력, 학습 진행률(완료/학습중/미학습 비율), JLPT 레벨별 학습 현황 바, 곡별 진행률

### 접근성
다크모드, 폰트 크기 조절 — 설정 화면에서 사용자가 직접 조작 가능하도록 구현

## 6. DB 스키마 (ERD)

**MySQL** 기준으로 설계. 4개 도메인, 총 12개 테이블. ERD 시각화: [우타고 DB 스키마](https://claude.ai/artifact/WGEFfXgHTLvEQ1S9KiP5sM)

- **사용자·설정**: `USERS`, `USER_SETTINGS`(다크모드/폰트/음원 계정 연결), `USER_STATS`(스트릭 등)
- **콘텐츠·가사·문법**: `SONGS`(provenance, content_status 필드 포함), `SONG_LINES`(원문+의역+타임코드), `SONG_LINE_READINGS`(사용자 모국어별 발음 표기 — 노래가 아니라 "보는 사람" 기준이라 별도 테이블로 분리), `GRAMMAR_POINTS`
- **사전·단어 매핑**: `WORDS`(마스터 사전, jlpt_level은 내부용/비노출), `WORD_MEANINGS`(다의어 빈도순 나열), `WORD_EXAMPLES`(source_type으로 마스터 예문/곡-문맥 예문 하이브리드), `SONG_LINE_WORDS`(소절-단어 매핑)
- **단어장·학습·SRS**: `WORDBOOKS`, `WORDBOOK_ITEMS`(SM-2 단순화 SRS 필드: next_review_at/interval_days/repetition_count/ease_factor 포함), `USER_SONG_PROGRESS`

**설계 원칙**: 곡마다 `provenance`(원문 확보 경로, AI 가공/검수 여부) 필드로 향후 라이선스 콘텐츠 전환 대비. 예문은 `source_type`으로 마스터 사전/곡-문맥 하이브리드 재사용. 발음 표기는 노래 자체 속성이 아니라 "보는 사용자의 모국어"에 종속되므로 `SONG_LINES`와 분리한 `SONG_LINE_READINGS` 테이블로 설계.

**다음 단계**: 실제 `CREATE TABLE` DDL 작성 (인덱스·제약조건 포함) — 8번 항목 참고.

**시사점**
- 문법 학습 페이지는 세 앱 모두 없음 → **우타고의 확실한 차별화 지점**, 계속 밀고 갈 것
- 완전한 다국어·양방향(모국어별 발음 자동 전환) 구조도 아직 아무도 제대로 구현 안 함 → 우타고의 잠재적 차별화 지점
- SRS·플래시카드·게이미피케이션(스트릭, 미니게임)은 이미 구현되어 있어 더 이상 독자적 차별점이 아님 → 완성도로 경쟁, 리소스는 차별화 포인트에 집중
- **우타코토의 AI 자동 콘텐츠 생성 파이프라인이 우타고 전략의 가장 큰 전환점** — "수작업 큐레이션"에서 "AI 보조 큐레이션"으로 전략 수정 (0번 항목 참고)
- 콘텐츠 소싱 모델이 앱마다 다름: 자동 매칭+AI가공(우타코토) / 사용자 수작업 싱크·UGC(우타노트) / 자체 고정 큐레이션(한음). 우타고는 우타코토의 AI 가공 아이디어를 차용하되, 가사 원문 출처는 더 깨끗한 경로를 지향
- JLPT 레벨 노출 여부, 예문 소스(마스터 사전 vs 곡별 맥락) 등 재검토 여지 — 5번 항목에 반영
- 전반적으로 리뷰 수가 적어 압도적 승자가 없는 초기 단계 시장 → 차별화 포인트만 명확하면 진입 여지 있음
- 두 경쟁 앱 모두 음악 검색/연동 기능에서 실사용 중 에러가 발생 → 외부 음원 API 연동 난이도를 넉넉히 잡을 것
